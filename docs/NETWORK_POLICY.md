# Сетевая политика

## Что гарантирует cii

1. **Deny by default.** Каждый модуль заранее объявляет хосты, к которым ему нужно обращаться, и зачем (`netx.Rule`). Любой другой хост, в том числе цель редиректа, отклоняется до отправки первого байта. Правила привязаны к модулю: модуль A не может воспользоваться хостами модуля B.
2. **Журнал соединений.** Каждый запрос — разрешённый, неудавшийся или заблокированный — записывается в `ledger` и выводится в отчёте (`network` в JSON).
3. **`--plan` говорит правду.** Он печатает ровно те правила, по которым работает политика. Другого пути в сеть у кода нет: весь HTTP и все «сырые» сокеты идут через `internal/netx`. Когда модуль подключается к уже найденному адресу (TCP-замеры и ICMP в `cii route`), netx пропускает только адрес, который сам вернул при разрешении этого объявленного имени для этого модуля, или адрес, который сам объявлен хостом. Сырой ICMP-сокет модулю не выдаётся: он получает обёртку, которая отправляет пакеты только на такие адреса.
4. **`--offline` ничего не отправляет.** Политика остаётся пустой, адреса берутся с интерфейсов, поиск идёт по локальным базам.
5. **Нет отправки результатов.** Нет функции «поделиться отчётом», счётчиков запусков, телеметрии, автообновления, загрузки отладочных логов.
6. **Нет удалённого кода.** cii ничего не скачивает для исполнения: ни скриптов, ни бинарников, ни «рекламных блоков».
7. **Данные — только у первоисточника.** `cii data update` скачивает базы напрямую у издателей (DB-IP, IPinfo, MaxMind), а не с серверов авторов cii. Запускается только явно.
8. **Прокси не обходится.** Весь HTTP идёт через прокси, если он задан флагом `--proxy` или переменными окружения `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY` (с учётом `NO_PROXY`). В обоих случаях «сырые» соединения и DNS-запросы (DNSBL, SMTP-проба, iperf3, проверки цензуры, ICMP и TCP-замеры `cii route`) запрещены и показываются как «неизвестно» с причиной: иначе они ушли бы мимо прокси и раскрыли реальный адрес. Решение «прокси в силе» принимается один раз при старте и одинаково для всех модулей.
9. **Секреты не утекают.** Токены вычищаются из URL в ошибках, логах и `manifest.json`.

Неизбежная оговорка: проверить доступность сервиса можно только запросом к нему. Поэтому цели проверок и echo-сервисы видят ваш IP — так же, как при обычном заходе браузером. Список echo-сервисов можно заменить на свой, см. [CONFIG.md](CONFIG.md).

## Уровни допустимости проверок (ToS/FUP)

| Уровень | Что это | Режим |
|---|---|---|
| **A** | Анонимный запрос к публичной странице или эндпоинту, разбор кода ответа, редиректа, региона в ответе | по умолчанию |
| **B** | Внутренние API с публичными client ID, которые сервис сам встраивает в свой веб- или мобильный клиент, вместе с заголовками этого клиента (в том числе `Origin`/`Referer` сайта того же сервиса, к API которого идёт запрос); страницы проверки адреса у сервисов риска: демо-виджет `ipinfo.io/widget/demo/{ip}`, страница `scamalytics.com/ip/{ip}` и главная ip2location.com в том виде, в каком их получает посетитель сайта, включая одноразовый токен, который страница выдаёт посетителю для его собственного адреса (решение владельца проекта, подробности в [RISK_CHECKS.md](RISK_CHECKS.md)) | только с `--extended` |
| **C** | Чужие учётные записи, чужие API-ключи, постоянные демо-ключи и демо-токены со страниц (годные для любых адресов), `Origin`/`Referer` чужого сайта, а также демо-эндпоинты, через которые сервис показывает данные своего платного API (кроме трёх страниц риска, явно перечисленных в уровне B), обход CAPTCHA и антибот-защиты, закрытые бинарники, удалённое исполнение кода | никогда |

Как устроен уровень B:

- проверка помечена уровнем B в каталоге; без `--extended` она не выбирается, её хосты не попадают в политику, и сеть к ним не пускает даже при ошибке в коде;
- `cii --plan --extended` показывает, какие хосты добавятся, ничего не отправляя;
- все сторонние идентификаторы лежат в одном файле `internal/clientids/clientids.go`, чтобы их было легко проверить или заменить;
- результаты помечены `*` в тексте и `"extended": true` в JSON;
- отказ, смена API или ключа у сервиса превращается в `unknown`/`error`, а не в ложный «доступно».

Дополнительные правила:

- **Частота.** Один запрос на проверку за запуск, ограниченная параллельность, соблюдение `429` и `Retry-After`, без повторов-штормов.
- **User-Agent.** По умолчанию честный: `cii/<версия> (+https://github.com/arngory/cii)`. Браузерный UA модуль может запросить только явно и с указанием причины: некоторые сайты отвечают не-браузеру иначе, и проверка без него даёт ложный результат.
- **Платные базы рисков** (IPQS, AbuseIPDB, Scamalytics, ipdata и т.п.): их API вызываются только с **вашим** ключом из конфига, без ключа такая проверка отключена. Исключение уровня B (`--extended`) — общедоступные страницы проверки ipinfo.io, Scamalytics и ip2location.com, как их видит посетитель; страницы за капчей или Cloudflare-проверкой и демо, работающие через ключ сайта, не используются.
- **DNSBL.** Опрос только через ваш собственный или локальный резолвер. Ответы-заглушки `127.255.255.x` (запрос через публичный резолвер, превышен лимит) считаются «недоступно», а не «чисто». Используются только списки, где разрешён бесплатный доступ.
- **Бенчмарки** не вызывают ничего, что само отправляет результаты (Geekbench исключён). Лицензии сторонних программ (например, Ookla) cii за пользователя не принимает.

Это инженерная политика, а не юридическая гарантия: условия конкретных сервисов меняются, и ответственность за частоту и цель запусков остаётся на пользователе.
